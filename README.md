# MMRec — Multimodal Sequential Recommendation for Micro-Video

A complete, reproducible recommendation system for short-video feeds, built on
**MicroLens-100K**. It starts from a correct sequential-recommendation stack
(chronological splits, causal SASRec, full-ranking evaluation with seen-item
masking) and then asks one focused research question:

> Pure item-ID models depend on collaborative signal, which is scarce for
> low-frequency, long-tail and cold videos. Do **text and cover-image content
> features** fix that — and if the answer is "partly", where exactly does the
> gain come from?

The project is organised so that the answer is *measured*, not asserted: every
claim below is backed by an artifact under `results/`, generated by a command
that is written down.

---

## Project overview

```
   item ID ──────────────┐
   text  (384-d) ────────┼──► modality projections ──► fusion ──► e_i
   image (768-d) ────────┤        (LayerNorm+Linear)   concat    (128-d)
   video (1024-d, opt.) ─┘                              gated
                                                            │
   user history [i1..iL] ──► item embeddings ──► causal Transformer ──► h_u
                                                            │
                                        score(u, i) = h_u · e_i
                                                            │
                              ┌──────────────┬──────────────┴──────────────┐
                              ▼              ▼                             ▼
                        overall Recall   cold-item Recall          long-tail Recall
```

Baselines: Popularity, BPR-MF, SASRec (ID-only).
Main model: **MM-SASRec** with concatenation or gated fusion, optionally trained
with **ID dropout** so that it cannot lean on the collaborative branch.

## Motivation

MicroLens-100K is extremely sparse and heavily long-tailed: at base-split
training frequencies the median item has a handful of interactions, a few hundred
items never appear in a training target at all, and the tail holds a large share
of the catalogue (exact figures in the generated table below). A pure-ID
sequential model has nothing to learn for those items. Content features are
available for **every** item, so the interesting questions are:

* Does multimodal content improve overall ranking at all?
* Text or image — which carries more signal for micro-video?
* Is simple concatenation enough, or does adaptive gated fusion help?
* Does the ID branch *suppress* the content branches, and does ID dropout fix it?
* Do the gains concentrate exactly where collaborative signal is weakest?

Feature row `r` belongs to raw item id `r`. This is **verified, not assumed**: the
pipeline builds an explicit `raw_item_id → feature_row` table and a unit test runs
the encoder on a *permuted* id space to prove the mapping path is real.

No large backbone is trained. Pre-extracted features go in, lightweight
projections come out.

## Data leakage policy

| signal | source |
|---|---|
| item frequency, popularity buckets | **training interactions only** |
| negative sampling distribution | training interactions only |
| cold-item selection | training protocol + fixed seed |
| `x_label` / likes / views | **not used at all** — full-lifetime aggregates that cannot be shown to be causally clean |
| evaluation | full ranking over the whole catalogue, with the user's own history masked and the ground-truth target explicitly protected |

`ProcessedData.assert_no_target_leak()` re-checks on every load that no validation
target appears in the train history and no test target appears in the train+val
history. Details in [`docs/evaluation_protocol.md`](docs/evaluation_protocol.md).

## Models

| model | item representation | notes |
|---|---|---|
| `popular` | training frequency | sanity floor |
| `bpr` | static MF, pairwise BPR loss | static collaborative filtering |
| `sasrec` | `nn.Embedding` | ID-only sequential baseline |
| `mm_sasrec` | `MultimodalItemEncoder` | ID + text + image (+ video), concat or gated fusion |

All sequential models share **exactly the same** positional encoding, causal
Transformer, loss, negative sampler, optimiser and evaluator. The only thing that
changes between `sasrec` and `mm_sasrec` is how the item embedding table is
produced — which is what makes the comparison meaningful.

**Missing modalities** are tracked with an explicit availability mask. A missing
modality gets exactly zero fusion weight and its embedding is zeroed before the
gate network; it is never fed to the model as a zero vector. See
[`docs/design.md`](docs/design.md) §3.

**ID dropout** (`id_dropout_prob`) randomly removes the ID branch during training,
forcing the model to explain items from content alone. This is the direct test of
the "ID dominance" hypothesis.

## Training

* autoregressive next-item training over **all** non-padding positions
* sampled softmax over 128 negatives, temperature 1.0
* negatives can never be PAD, the positive target, or any known interaction
* AdamW, AMP, gradient clipping (5.0), early stopping on validation NDCG@10
* one config file per experiment; nothing is hard-coded in the source

```bash
python scripts/train.py --config configs/mm_sasrec_gated.yaml
python scripts/train.py --config configs/sasrec.yaml --training.seed 2026
python scripts/train.py --config configs/sasrec.yaml --resume results/runs/<id>/last.pt
```

Every run writes `config.yaml`, `environment.txt`, `training_log.csv`,
`metrics.json`, `train_summary.json` and the raw per-user ranking arrays into
`results/runs/<run_id>/`.

## Evaluation protocol

Leave-one-out, strictly chronological:

```
history : i1 i2 i3 i4 i5 i6 i7
train   : i1 i2 i3 i4 i5        (autoregressive shift inside this window)
val     : i6                    test: i7
```

Full ranking over the entire catalogue (its size is in the generated dataset
table). Candidate dot-products are computed in item chunks, while the
batch-level full score matrix is retained for exact ranking — no candidate
pre-filtering, no approximate top-k. The user's own history is masked, the
ground truth never is. Metrics: `Recall@{5,10,20}`, `NDCG@{5,10,20}`, plus
`MRR@20` and `Coverage@20`.

**Validation is used for early stopping and is therefore optimistically biased.**
Test numbers are reported from the best checkpoint and are the only ones used for
conclusions.

Cold-item and long-tail results are computed by *slicing the same ranking pass*
that produced the overall numbers, so the tables cannot contradict each other.

## Results

MicroLens-100K, full ranking over the whole catalogue, test split, mean ± std
over seeds where more than one seed finished. `TBD` means the run has not finished —
**no number in this repository is estimated or filled in by hand**. Tables are
regenerated from `results/tables/*.csv` by `python analysis/update_readme.py`.

Every finished base-split configuration is listed: the ordering baseline
(Popular → BPR → SASRec), the regularisation control, and the modality/fusion
ablations. Rows without a ± are single-seed ablations — their seed spread has
not been measured, so where a difference is no larger than the multi-seed
standard deviation shown on the rows that have one, it is **not** interpreted
as real.

### Cold-item evaluation

Simulated cold split: a fixed share of items (counts in the generated dataset
table) have **every training interaction removed**; they keep their content
features and their ID representation is zeroed at inference for every model, so
the collaborative signal for them is gone by construction.

`Cold *` = full ranking over all items for users whose target is cold.
`ColdOnly *` = ranking restricted to the cold catalogue (a sharper measure of
content quality).

The table above is the result: whether the ID-only model is exactly zero and how
much the multimodal model recovers is read off it (and off the generated findings
below), not remembered here. What the comparison is designed to test is that
content features can do something the collaborative signal structurally cannot.

Two things sit outside the headline and are reported because they are awkward
for the story. First, the ID-dropout variant — the base-split headline config —
is the **weakest** of the three content-capable cold rows in the table below,
i.e. on this evidence ID-dropout trades away content reliance rather than
strengthening it. Second, the `Cold *` columns are tiny next to `ColdOnly *`:
in full-catalogue ranking the target has to beat the whole catalogue, and the
restricted columns are the ones that isolate content quality. Each cold row is
one seed, so both are directions to confirm rather than settled effects.

Ranks use the **tie-neutral midpoint policy** (`docs/evaluation_protocol.md`):
with an optimistic policy every cold item tied at score 0 would be reported as a
perfect hit, which would be a measurement artefact rather than a result.

## Semantic ID extension

Content embeddings are quantised into Semantic IDs with an RQVAE, and a small
causal Transformer generates the next item's ID instead of scoring vectors.

**Status: paused** while the discriminative results stabilise. The numbers below
quantise the raw per-modality-normalised text+image features and are recorded in
`artifacts/semantic_id_report_content.json`; they do not depend on any
recommender checkpoint. (`artifacts/semantic_id_report_fused.json` does — it was
built from a pre-fix run's fused embeddings and is legacy.)

| | |
|---|---|
| quantiser | RQVAE, 4 levels × 256 codes, latent 64 |
| reconstruction cosine | 0.681 (`artifacts/semantic_id_report_content.json`) |
| codebook utilisation | `[1.0, 1.0, 1.0, 1.0]` |
| unique Semantic IDs | 19 692 / 19 738 items |
| collision rate | **0.233 %** |

Getting there required fixing three things that are easy to get wrong, all
documented in the code:

* **residual-aware code re-seeding** — seeding level *k* with full encoder
  outputs makes those codes unreachable, because by level *k* the residual is far
  smaller than `z`;
* **the commitment term** — training only the codebook loss leaves the encoder
  free to drift away from the codes;
* **per-modality normalisation** — raw text is unit-norm while raw image has norm
  ≈ 26, so an un-normalised concatenation lets the image block dominate.

An early variant with random codebook initialisation and a codebook-only loss
collided heavily enough to make generative retrieval meaningless. No artifact
from that variant was archived, so no number is quoted for it. The residual
0.233 % of collisions in the current configuration is handled explicitly rather
than ignored: the mapper stores `SID → [items]` and expands colliding candidates.

Decoding is constrained by a prefix trie (`PrefixConstraint`), so the generator
can only emit a code tuple that corresponds to a real item — never a hallucinated
one, and never a random fallback. See `scripts/train_rqvae.py`,
`scripts/sweep_rqvae.py` and `scripts/train_generative_rec.py`.

## Reproducibility

```python
set_seed(seed)   # random, numpy, torch (CPU + CUDA), PYTHONHASHSEED
```

Negative sampling, cold-item selection and popularity bucketing all use
explicitly seeded generators. Training data is fully in memory with
`num_workers = 0`, so there is no worker-seeding ambiguity. Checkpoints store a
dataset hash and **refuse to load** into a dataset with a different item mapping
or cold split.

GPU kernels are not guaranteed to be bitwise deterministic. Runs are reproducible
in distribution: same config + same seed ⇒ identical data order, negative samples
and initialisation.

## Limitations

* MicroLens-100K has short histories (median 6 interactions), which caps what any
  sequential model can learn. Conclusions may not transfer to longer-history
  settings.
* The 100K HuggingFace subset ships **no item titles or captions**, so the case
  study illustrates semantics with nearest neighbours in the content embedding
  space rather than with text. It also means we cannot report title-based
  qualitative examples.
* Video features are wired into the architecture and configurable, but the main
  tables use ID + text + image; the video ablation is reported separately.
* The cold protocol is *simulated* (interactions removed by a fixed seed), not a
  naturally occurring cold-start stream.
* Validation is used for early stopping, so validation numbers are optimistic.
  Test numbers are reported from the best checkpoint.
* Generative recommendation is a small Transformer over semantic IDs, not an LLM;
  it is a comparison point, not a claim that generative retrieval wins.

## Roadmap / extension

The `rqvae.py` + `semantic_id.py` + `generative_rec.py` modules implement the
Semantic-ID extension: content embeddings are quantised into code tuples,
collisions are measured and handled, and a small causal Transformer generates the
next item's Semantic ID under a prefix constraint so it can only ever emit a real
item. See `scripts/train_rqvae.py` and `scripts/train_generative_rec.py`.
